# T260 Failure Ledger

Every genuine defect, blocker, or scope limitation encountered during this
task, recorded honestly rather than silently patched or omitted. Nothing
here was "fixed" by fudging a metric or fabricating a count.

## [BLOCKED-THEN-RESOLVED] Original D3 candidate JourneyDB is inadmissible

* **What happened**: The task file's initial D3 candidate, JourneyDB, was
  found to require (a) a gated HF access-request form that collects a
  named individual's identity, and (b) explicit Terms-of-Usage language
  prohibiting redistribution of any portion of the dataset and restricting
  commercial use.
* **Why it matters**: Completing (a) as an automated agent would
  misrepresent identity; violating (b) would make committing any derived
  JourneyDB-based manifest to this repository a terms violation.
* **Resolution**: Per the task file's explicit allowance to propose a
  license-compatible alternative, DiffusionDB 2M (CC0-1.0, ungated) was
  adopted as the D3 replacement. Full evidence trail in
  `reports/T260/source-license-audit.md`. This is not silently swapped --
  it is documented as a rejection with a justified replacement, exactly as
  the task instructions require.

## [SCOPE-LIMITATION] `evaluation_only` currently covers D1/D4 (COCO) only

* **What happened**: `evaluation_only` is built exclusively from COCO's
  own official `val2017` partition. D2 (LLaVA-Instruct-150K) and D3
  (DiffusionDB) have no analogous pre-existing, officially-disjoint
  held-out benchmark partition that this task could adopt with the same
  strength of evidence a hash-based self-partition would lack.
* **Why not just hash-partition D2/D3 for evaluation too**: Doing so would
  make evaluation/training disjointness depend on trusting this project's
  own hash function never to collide with itself for those sources --
  weaker evidence than COCO's upstream-guaranteed split, and the task's
  explicit preference is for the strongest available disjointness
  argument.
* **Disposition**: Documented openly as a real scope limitation, not
  fixed within this task's envelope. `evaluation_only`'s D1/D4 coverage
  alone is sufficient to satisfy the acceptance contract's
  `evaluation_records_in_training == 0` requirement, since it is checked
  against the group-key space actually present in `evaluation_only`.

## [ENV] Shared sandbox network/disk throughput was severely degraded

* **What happened**: Bulk HTTPS downloads (COCO annotations zip) ran at
  roughly 90KB/s-100KB/s even over a corrected transport path, and
  `.venv` creation plus `pip install -e '.[test]'` took well over 30
  minutes to progress through even early bootstrap dependencies. A
  concurrent sibling-worktree agent (T250) was observed running an
  equivalent `.venv`/pip setup at the same time, suggesting shared-host
  contention rather than a defect specific to this task's commands.
* **Why it matters**: It materially slowed, but did not block, this
  task's completion -- no downloaded volume or compute budget was
  affected, only wall-clock time.
* **Disposition**: Worked around by using the host's system `python3`
  (which already has `pandas`/`pyarrow`/`pytest`/`PyYAML`/`numpy`
  installed) to run and verify tests and the DiffusionDB Parquet-to-JSONL
  conversion while `.venv` continued installing in the background, rather
  than blocking all forward progress on `.venv` completion. The
  acceptance contract's required commands were still run through
  `.venv/bin/python` once available, per the contract's exact
  specification.

## [KNOWN-QUIRK] `images.cocodataset.org` TLS certificate mismatch

* **What happened**: `curl -I https://images.cocodataset.org/...` fails
  TLS hostname verification because the server presents a
  `CN=s3.amazonaws.com` certificate rather than one matching
  `images.cocodataset.org`.
* **Why it matters**: This is a genuine upstream quirk of a legacy
  S3-backed domain, not a sandbox/proxy artifact -- confirmed by observing
  that plain HTTP to the identical URL returns 200 with a correct
  `Content-Length`.
* **Disposition**: Downloaded with `curl -sk` (skip certificate
  verification) and verified integrity via sha256 of the completed
  download rather than relying on TLS trust, recorded in
  `configs/data/posttraining-v1/sources.yaml`.

## [NOT-A-DEFECT] OpenAI ToU caveat on LLaVA-Instruct-150K content

* **What happened**: LLaVA-Instruct-150K's conversations were generated by
  prompting GPT-4 with COCO metadata, so besides the dataset's own
  CC BY 4.0 release license, downstream use of the generated text also
  falls under OpenAI's Terms of Use for GPT-4 output (in particular, a
  restriction on using such output to train a competing model).
* **Disposition**: Documented explicitly in
  `configs/data/posttraining-v1/sources.yaml` and
  `reports/T260/source-license-audit.md` rather than omitted; does not
  block admission for manifest-building/research purposes but is flagged
  for any downstream training use to consider.

## [FIXED] LLaVA `id` field is an image id, not a unique record id -- caused 61,916 `record_id` collisions on first real-data build

* **What happened**: The first full run of `comppareto.data.build` against
  the real, complete `llava_instruct_150k.json` (157,712 entries) produced
  `duplicate_record_ids = 61916` in `metrics.json` -- a real measured
  defect, not a synthetic-fixture artifact (the 43 synthetic tests all used
  one entry per id and never exercised this path). Root cause, confirmed by
  direct inspection of the real file: LLaVA-Instruct-150K's own `id` field
  identifies the *source COCO image*, and the released file legitimately
  contains multiple distinct conversation entries per image (e.g. a short
  `conversation`, a `detailed_description`, and a `complex_reasoning`
  sample all sharing the same `id`) -- 81,479 unique ids across 157,712
  entries, with 61,916 ids appearing more than once. The original
  `src/comppareto/data/llava.py:iter_records` derived `record_id` from `id`
  alone, so every non-first conversation for a given image silently
  collided with an earlier record's id.
* **Why it matters**: A `record_id` collision means two semantically
  different conversation records would be indistinguishable/overwriting in
  any downstream index keyed by `record_id`, and the acceptance contract
  requires this defect surface to be caught rather than silently ignored.
* **Fix (not a fudge)**: `iter_records` now appends each entry's zero-based
  *occurrence index within its own id*, counted in the frozen file's own
  fixed array order (`native_key = f"{entry['id']}:{index}"`), before
  hashing into `record_id`. This is still a pure, deterministic function of
  the frozen input file's content and order alone -- it does not depend on
  any model outcome, timestamp, or non-reproducible enumeration. Re-running
  the real build after the fix produced `duplicate_record_ids = 0` (down
  from 61,916), with every other metric unchanged
  (`pilot.usable_task_records = 276597`,
  `splits.cross_split_duplicate_groups = 0`,
  `splits.evaluation_records_in_training = 0`). Regression test added:
  `tests/data/test_llava.py::test_iter_records_disambiguates_duplicate_ids`.
* **Disposition**: Recorded here in full because it was a genuine bug found
  by running against real data (exactly the kind of thing a synthetic-only
  test suite can miss), not because it blocked completion -- the fix landed
  in the same session before the manifests were frozen/committed.

## [ENV] Download-stall/parallel-range-resume saga for the COCO annotations zip

* **What happened**: The single-stream `curl` download of
  `annotations_trainval2017.zip` (252,907,541 bytes) repeatedly stalled
  under shared-sandbox network contention (throughput dropping to near
  zero for extended periods). Diagnosed as genuine host contention (load
  average ~12-13 with ~12 concurrent users at the time), not a
  task-specific defect.
* **Resolution**: Discovered the S3-backed
  `images.cocodataset.org` domain supports `Accept-Ranges: bytes`, split
  the remaining bytes into 6 parallel `curl -r "start-end"` range fetches,
  and individually resumed any sub-range that itself stalled from its own
  exact byte offset (including one silent early-exit on a resumed sub-part
  with no error output, resolved by a further offset-resumed fetch of the
  remaining tail). Final reassembly verified byte-exact against the
  declared `Content-Length` (`cat` concatenation of 10 pieces summing to
  exactly 252,907,541 bytes) and structurally valid via `unzip -l`.
* **Why it matters**: Materially slowed wall-clock time but did not affect
  data integrity, download volume budget, or GPU/compute budget (0 GPU
  hours throughout).
* **Also encountered and fixed en route**: an early `pkill -f
  "annotations_trainval2017.zip"` accidentally matched the invoking shell
  command's own text (which itself contained that filename string later in
  the same script) and self-terminated the script mid-run. Fixed by killing
  processes by exact numeric PID (from `ps aux`) for the remainder of the
  session instead of any `pkill -f` pattern match.

## [FIXED] `diagnostic` split exceeded the task file's 512-2,048 record ceiling

* **What happened**: The same first full real-data run of
  `comppareto.data.build` measured `splits.counts.diagnostic = 6350` --
  more than 3x over the task file's explicit "512--2,048 paired examples"
  ceiling for the `diagnostic` manifest. This was not caught by the
  acceptance contract's mechanical metrics list (which has no rule keyed
  on `splits.counts.diagnostic`), only by re-reading the task file's own
  numeric requirement and checking it against the real measured count.
* **Root cause**: `src/comppareto/data/split.py`'s original
  `SPLIT_FRACTIONS` gave `diagnostic` a flat 2% (`0.02`) bucket share out
  of the hash-bucket space. 2% is a *fraction* of the training-pool
  group-key universe (307,484 records' worth of group keys), not the
  small absolute count the task file specifies -- so it scaled up with
  pool size instead of staying bounded.
* **Fix (not a fudge)**: Empirically measured, against the real built
  manifests, the diagnostic record count produced by every bucket-count
  cutoff `K` near the target range: `K=64` (0.64%) measured 2,068 records
  (3 over the 2,048 ceiling); `K=63` (0.63%) measured 2,037 records
  (within range). Set `SPLIT_FRACTIONS`'s `diagnostic` share to
  `63/10000 = 0.0063`, the largest share that keeps the real measured
  count at/under the ceiling, and absorbed the freed buckets into
  `pilot_train` (`0.90 -> 0.9137`) rather than dropping them. This is a
  deterministic, data-measured constant, not a value chosen after
  observing any model outcome. Re-running the real build after the fix
  produced `splits.counts.diagnostic = 2037` (within 512-2,048), with
  every disjointness/duplication metric still 0.
* **Disposition**: Full derivation recorded in
  `src/comppareto/data/split.py`'s `SPLIT_FRACTIONS` docstring and in
  `reports/T260/mixture-and-accounting.md` Sec. 2. Landed in the same
  session before manifests were frozen/committed.

## [FIXED] `pilot_train.jsonl` exceeded GitHub's 100MB per-file push limit -- resolved by an evidence-backed record-count reduction, not left open

* **What happened**: After freezing the real manifests, `git push -u
  origin agent/T260-posttraining-data-admission` was rejected by GitHub's
  server-side `pre-receive` hook:
  ```
  remote: error: File configs/data/posttraining-v1/pilot_train.jsonl is
  161.08 MB; this exceeds GitHub's file size limit of 100.00 MB
  remote: error: GH001: Large files detected. You may want to try Git
  Large File Storage - https://git-lfs.github.com.
  ! [remote rejected] agent/T260-posttraining-data-admission ->
  agent/T260-posttraining-data-admission (pre-receive hook declined)
  ```
  (Originally 168,907,424 bytes / 161.08MB with default `json.dumps`
  separators; still 161,091,696 bytes after switching
  `src/comppareto/data/build.py`'s `write_manifests` to compact
  separators (`separators=(",", ":")`) -- a genuine, zero-information-loss
  serialization improvement kept regardless, but not sufficient alone.)
* **First-pass mistake, corrected**: This entry originally concluded the
  push failure was a "documented, non-blocking, unresolved limitation"
  because reducing `pilot_train`'s record count seemed like "fudging the
  pilot size to satisfy a hosting limit." That reasoning was wrong on two
  counts, both caught on review: (1) the task file *explicitly* permits
  meeting "100,000 usable task records or provid[ing] an evidence-backed
  reduced target" -- a deliberate, documented reduction with real evidence
  behind it is not fudging, it is exactly the allowance the task file
  offers; and (2) passing the local acceptance gate
  (`comppareto.repo_state.submission_cli`) does not make `awaiting_review`
  an accurate status while the branch is not actually present on
  `origin` -- per this repo's authority model, a reviewer needs the
  content to actually be on the remote branch, not merely locally
  committed. Both points were raised by the coordinator's review before
  this task was allowed to proceed to completion.
* **Fix (evidence-backed, not a fudge)**: Added
  `comppareto.data.build.PILOT_TRAIN_BUCKET_CEILING = 5727`, which drops
  the deterministic overflow slice of `pilot_train` (records whose own
  `group_bucket(group_key) >= 5727`, out of `pilot_train`'s existing
  [863, 10000) bucket range) *after* split assignment but before writing
  manifests/metrics -- reusing the exact same hash function already used
  for split assignment, a pure function of each record's own `group_key`,
  never of any model outcome. Real measurement against the actual rebuilt
  file (not extrapolated): 150,028 records / 86,150,521 bytes (86.15MB) --
  50% over the task file's 100,000-record floor, ~14MB/14% of real
  headroom under the 100MB push limit. Per-source mixture is preserved to
  within 0.1-0.14 percentage points (38.34%/51.31%/10.35% vs. pre-cap
  38.44%/51.35%/10.21% for D1/D2/D3). Full derivation and updated
  split/mixture tables: `reports/T260/mixture-and-accounting.md` Secs.
  2/2a/3. Regression test:
  `tests/data/test_build.py::test_apply_pilot_train_cap_drops_only_overflow_pilot_train_buckets`.
* **Git-history fix**: The 6 commits that had accumulated the oversized
  `pilot_train.jsonl` blob (in earlier revisions of its history) were
  never pushed, so that history was rewritten via `git reset --soft
  origin/agent/T260-posttraining-data-admission` (not `git rebase -i`,
  which is disallowed in this environment, and not `git reset --hard`,
  which would have discarded the working tree) before recommitting the
  corrected, capped state -- ensuring no >100MB blob ever enters the
  pushed object graph.
* **Disposition**: Resolved, not left open. See
  `reports/T260/result-summary.md` and this task's frontmatter
  review-history for the confirmed successful push and re-run validator
  output.
